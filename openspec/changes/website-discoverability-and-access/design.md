## Context

See proposal.md — Why. What shapes the approach is what the site already is.

`website/tools/sync-docs.mjs` is the only writer of page content: it walks `git ls-files docs/**`,
rewrites every relative link, derives frontmatter from the first `# Heading`, and fails the build on
a link it cannot resolve or a sidebar entry it cannot find. `docs/` is the single source and the
site never holds a second copy of a page — the README says so and the sync enforces it.

Three constraints stand around the work:

- **No image processing at build time.** `astro.config.mjs` uses `passthroughImageService()` on
  purpose, so `sharp` and its LGPL libvips binary never run. `tools/check-licences.mjs` names that
  exception explicitly. Any solution that renders images during the build reopens both.
- **The docs collection is ours, not Starlight's.** It comes from a `glob()` loader over
  `generated/docs`, which is why the sidebar is hand-kept and guarded rather than autogenerated.
  Anything Starlight derives from its own collection has to be checked before it is assumed.
- **Apache under Plesk, no adapter.** The deploy workflow writes `.htaccess` files and then asks
  the live domains what they actually serve. There is no edge function and no SSR.

The demo is a separate artefact on a separate subdomain, built from `demo/` and deployed by the same
workflow, with an SPA fallback that rewrites every non-file request to `index.html`.

## Goals / Non-Goals

**Goals:**

- Everything a crawler or an assistant reads before deciding to fetch a page in full is present and
  page-specific: description, social card, structured data, freshness.
- Every derived value keeps a single source. A description comes from the page, a version from
  `Directory.Build.props`, a date from git.
- The four accessibility defects are fixed at the token or component that causes them, not patched
  at the call site.
- The build fails when the site regresses, the way it already fails on an unresolvable link.

**Non-Goals:**

- Per-page generated social cards. Chosen against below.
- Rewriting the fifteen meta-refresh redirects into `.htaccess` 301s. They carry `noindex` and a
  canonical, Google follows them, and a second copy of the redirect list in a shell heredoc is a
  second thing to keep true.
- Converting the screenshots to WebP or AVIF. Worth doing, unrelated to discoverability, and it is
  a change about `assets/media/` rather than about the site.
- Anything under `openspec/specs/`. The website is not part of the platform contract.

## Decisions

### Descriptions are derived, not written

`sync-docs.mjs` already derives the title from the first heading. It gains the same treatment for
the description: after the title is stripped, take the first paragraph that is prose — skipping
blockquotes, the `<!-- derived-from-specs -->` marker, fenced blocks, images and headings — flatten
its markdown to text, and cut it to at most 160 characters at a sentence boundary, falling back to
a word boundary.

*Alternative rejected: a `description:` line in each of the 73 source documents.* It puts an SEO
artefact into files whose audience is a reader of the repository, GitHub renders the frontmatter as
a table above every one of them, and it creates 73 new opportunities for a description to describe
a page it no longer matches. Derivation cannot drift.

*Alternative rejected: hand-written descriptions in a lookup table in the website project.* Same
drift, and it breaks the rule the README states — the site never holds a second copy of a page.

The sync fails when a page yields no usable paragraph, so a new document cannot silently ship with
the generic fallback. This is the same guard the sidebar check already is.

### One social card, drawn once, committed

A 1200×630 card lives in `assets/brand/` as a committed PNG, produced from a committed SVG, and is
referenced as `og:image` and `twitter:image` on every page. `sync-docs.mjs` copies it into
`public/` beside the other brand assets, and fails when it is missing, exactly as it does for the
tour media today.

*Alternative rejected: per-page cards via `satori` + `resvg-js`.* It is the better result — a
documentation page shared into a Slack channel shows its own title — but it adds two runtime-weight
dependencies to a project whose licence gate is deliberately narrow, and it renders images during
the build, which is the thing `passthroughImageService()` exists to avoid. The card is one asset
and the site is one project; the ratio does not justify it. If documentation shares ever become a
real channel, this is where to revisit.

The card carries the icon and no brand name in an eyebrow position, following the cover rule the
articles already use.

### Structured data lives in one head component

`components.Head` is overridden with a component that renders Starlight's default and then appends
what is missing: the image tags, `og:type` corrected on the landing page, the icon set,
`theme-color`, and a JSON-LD block whose shape depends on the route.

- The landing page emits `SoftwareApplication` — name, category, `applicationCategory`,
  `operatingSystem`, licence, `codeRepository`, `programmingLanguage`, `softwareVersion`, `offers`
  at zero — plus `WebSite` and `Organization`.
- A documentation page emits `TechArticle` with `dateModified`, and a `BreadcrumbList` built from
  the sidebar group the page sits in.

`softwareVersion` is read from `Directory.Build.props` by `sync-docs.mjs` and written into a
generated JSON module the config imports. The props file is already the version single-source that
`bump-version.sh` writes and the release workflow verifies; a second literal in the website would be
the eighth place a version can be wrong.

*Alternative rejected: JSON-LD injected per page through frontmatter.* Our pages have no
hand-written frontmatter by design, and the breadcrumb is derivable from the sidebar the config
already declares.

### Freshness comes from git, and is emitted twice

`sync-docs.mjs` runs one `git log` per source document for its last commit date, writes
`lastUpdated` into the generated frontmatter — `docsSchema()` accepts it, and Starlight then renders
its own "Last updated" footer for free — and writes a route→ISO-date map into a generated JSON
module. `astro.config.mjs` imports that map and passes `serialize` to `@astrojs/sitemap` so every
`<url>` carries `lastmod`.

Starlight adds `@astrojs/sitemap` itself only when the integration list does not already contain it,
so declaring it explicitly replaces Starlight's copy rather than duplicating it. `@astrojs/sitemap`
becomes a direct dependency; it is already in the tree as Starlight's own, under MIT.

*Alternative rejected: Starlight's `lastUpdated: true`.* It reads git for its own content
collection. Ours is a `glob()` loader over generated files whose mtimes are the build's, so it would
date every page to the day of the deploy.

### The demo leaves the index

`demo/src/index.html` carries `<meta name="robots" content="noindex, nofollow">`, and
`demo/public/robots.txt` **allows** crawling.

That combination is deliberate and the two halves are not interchangeable. The SPA answers every
path with the same document, so a single `noindex` in that document covers the whole unbounded path
space at once — there is no page it can miss. A `Disallow: /` would defeat it: every page of the
docs site links to the demo, and a URL a crawler is forbidden to fetch but finds linked is indexed
from the link alone, as a bare URL with no snippet and no way to ever read the `noindex` that would
have removed it. Blocking the crawl is how a page gets stuck in the index, not how it leaves.

`robots.txt` therefore ships mainly so that it exists: today the request for it falls through the
deploy workflow's SPA fallback — `RewriteCond %{REQUEST_FILENAME} !-f` sends anything that is not a
file to `index.html` — and answers with the application shell under `content-type: text/html`. A
real file wins that condition. The deploy workflow's post-deploy check gains two assertions, that
`demo.loomweaver.dev/robots.txt` answers as `text/plain` and that the demo's document carries
`noindex`, so neither can regress silently.

*Alternative rejected: `Disallow: /` in the demo's robots.txt.* Argued above: it is the instruction
that would keep the demo in the index rather than remove it from it.

*Alternative rejected: canonicalising the demo to the docs root.* A canonical across hosts to a page
with different content is a hint search engines routinely ignore, and it would still leave an
unbounded space of 200-answering paths.

### The accessibility fixes are made where the value is set

- The card aside moves from `--sl-color-gray-3` to `--sl-color-gray-2`, taking it from 4.49:1 to
  8.57:1 in the dark theme. The 0.01 shortfall is not worth a bespoke colour.
- The landing page's secondary button border moves from `--sl-color-gray-5` to `--sl-color-gray-4`,
  which clears 3:1 against the page background in both themes. Verified by calculation before it is
  written, not after.
- A `:focus-visible` rule is added for the landing buttons and the consent-banner controls, using
  the accent as the ring and an offset so it reads over the button's own fill. Nothing in the
  shipped bundle defines one today, so this is an addition, not an override.
- The footer's "Cookie settings" button moves focus to the banner's first control when it opens it,
  and the banner returns focus to the button it came from when it closes.

A script under `website/tools/` computes the contrast ratio of the pairs the landing page uses and
fails when one drops below its threshold, so a token change cannot quietly reintroduce the defect.
This is the guard, and it is why the fixes are recorded as ratios rather than as colours.

### robots.txt names what it already allows

`sync-docs.mjs` writes `robots.txt`, so the AI-crawler section is written there beside the sitemap
line. Naming `GPTBot`, `ClaudeBot`, `Claude-Web`, `PerplexityBot`, `Google-Extended`, `CCBot` and
`Applebot-Extended` with `Allow: /` changes nothing a crawler is permitted to do — `User-agent: *`
already permits it — and states it unambiguously for the ones that look for their own name before
falling back. The file also points at `llms.txt` as a comment line.

## Risks / Trade-offs

**A derived description reads worse than a written one on some pages** → The first prose paragraph
of these documents is, by convention, what the page is about; the pages were written that way. The
cut is at a sentence boundary, so a description is a whole sentence or several. Where the result is
genuinely poor, the fix is to improve the page's opening paragraph, which improves the page too.

**160 characters is a guess about a moving target** → It is Google's long-standing practical limit
and no engine truncates below it. The number sits in one constant.

**One git invocation per document, ~76 of them, on every build** → Measured against the build it
sits in, this is noise; the sync already shells out to git once for the file list. If it ever is
not, a single `git log --name-only` pass over `docs/` replaces the loop without changing anything
that reads it.

**JSON-LD that disagrees with the page is worse than none** → Everything in it is derived: the
version from `Directory.Build.props`, the date from git, the breadcrumb from the sidebar the config
already declares, the licence from what the repository ships. Nothing is typed twice, so nothing
can disagree.

**The static card means a shared documentation page looks like a shared landing page** → Accepted,
and named above as the thing to revisit if documentation shares become a channel worth measuring.

**`noindex` on the demo removes a ranking domain** → It ranks for nothing today: it is an empty
shell with one title and no description, and every path answers 200. What it can do is dilute; what
it cannot do is rank. The link from every page of the docs site still carries its value.

## Migration Plan

The site is static and redeployed whole on every merge to `main` that touches it. There is no data
migration and no rollback beyond reverting the commit. The deploy workflow's post-deploy check is
extended in the same change, so the first deploy after merge either proves the new head, the new
robots and the new sitemap are live, or fails.

De-indexing the demo is the one step that is not instant: a `noindex` removes a URL when the crawler
next fetches it, which is why the robots.txt beside it must keep allowing that fetch. Expect the
demo's entries to disappear over the following weeks rather than at the deploy, and do not add a
`Disallow` in the meantime out of impatience — that is precisely what would freeze them in place.
