## Context

See proposal.md, Why. What shapes the approach is how the guides are already built.

- Every page under `docs/` opens with the derived-from-specs marker and the box that names the
  capabilities it explains. `website/tools/sync-docs.mjs` fails the site build for a page that is
  not in `website/sidebar.mjs`, and `docs-style-check` in `platform/` ratchets long sentences.
- The authoring guides all use one weaver, `notes`, generated by
  `npx @loomweaver/cli weaver --id notes --out src/notes`. A recipe on the samples page is whole
  files with the path they belong at, and the page states that everything lives inside
  `activate(ctx)` unless the path says otherwise.
- The samples page opens with a table naming which recipes the generator already writes. That table
  is the reader's first stop, so a recipe the generator half writes says so there.
- The navigation tree is a custom element. It has no manifest key and no `ctx.register*` call. A
  weaver writes the tags in its own template, needs `CUSTOM_ELEMENTS_SCHEMA` for Angular, and
  needs the `navigation` capability for the three `ctx` members the tree is built on:
  `activeContent`, `isShowingUnder` and `navigateContent`. Retitling the panel is a fourth,
  `retitleSurface`, under `contributions`.
- The working consumer is `demo/src/navigation`: `module-tree.ts` holds the declaration,
  `module-nav-view.html` the markup, `module-nav-view.ts` the filtering and the retitle effect,
  `navigation-actions.ts` the module-level bridge to `ctx`.
- The working stand-in session is `demo/src/session`: `session.ts` holds two snapshots and the
  switch, `session.plugin.ts` the three commands, `session-actions.ts` the rail item and its menu.
  The `auth-source` generator in `platform/libs/tooling/devkit/src/recipes/auth-source` writes
  the state half of the same thing, anonymous, user and admin with a `cycle` function, and
  nothing that calls it.

## Goals / Non-Goals

**Goals:**

- A reader who wants a sidebar navigation finds one page that tells the whole story and one
  recipe they can copy, and the page they land on from the reference table is that one.
- A reader trying the platform gets a session they can sign in and out of in the first hour,
  and knows what of it the generator writes.
- What the demo does beyond the bare element is written once, so the demo's source stops being
  the only place to learn it.
- The two AI-readable files know what this change adds, so an assistant asked for a sidebar
  navigation writes `<lw-nav-tree>` and not a list of its own.

**Non-Goals:**

- Completing `llms.txt` and `llms-full.txt` beyond what this change adds. That is
  `the-llms-files-carry-the-whole-contract`, which also decides how a guard holds them complete.
- Pointing from the demo at the docs, or from the docs at the running demo. That is
  `the-demo-points-at-the-docs`. This change adds exactly one pointer at the demo's source, in
  place of a pointer that was wrong for a reader from outside.
- A generator that writes recipe 11, or commands for what `auth-source` writes. Follow-up change,
  after the recipes have been read.
- Anything under `openspec/specs/`. Every behaviour the pages describe is already required.

## Decisions

### A page of its own in the weaver group, after sidebar surfaces

`docs/weaver/navigation-tree.md`, listed in the sidebar directly after "Surfaces in a sidebar".

*Alternative rejected: a section on the sidebar-surfaces page.* That page's subject is docking a
surface; the tree is what goes inside one particular kind of docked surface, and the story has
eight parts. A section that long would make the page it lives on about the tree. The
sidebar-surfaces page instead names the tree in "What your view's own body can use" and sends the
reader on.

*Alternative rejected: leaving it on the design-tokens reference and expanding the bullet.* The
reference is where a reader looks something up they already know exists. Nobody discovers a
feature there, and the two pull requests that documented the element only there are the evidence.
The bullet keeps the element's attributes and events, which is what a reference is for, and defers
the story.

### The page follows the demo, told with the notes weaver

The eight sections are what `demo/src/navigation` does, in the order a reader meets them: declare,
report and act, mark, fold, hide the unregistered, retitle, name for assistive technology, content
in an item. The code uses `notes` like every other guide, not the demo's modules, so that the
recipe compiles against the same generated weaver the reader has.

The declaration is data, a typed array of groups and destinations, because a tree written as
literal tags in the template cannot filter what nobody registered and cannot be renamed on a
language change. The demo's `ModuleArea` and `ModuleView` shapes are the model; the page's version
is smaller.

Two traps the page states as rules rather than warnings: give every group a `key`, because the
key falls back to the label and a translated label changes with the language; and drive
`collapsed` as `[attr.collapsed]="shut ? '' : null"`, because a boolean attribute is present or
absent, never `"false"`.

### The tree's capability is stated once, on the page

"To build a sidebar tree you need `navigation` and the element" is a connection the reader today
makes across two pages. The page states it in its second section, with the three `ctx` members
the tree is built on and the fourth for retitling. The manifest line in recipe 11 declares
`['contributions', 'navigation']`, and the recipe's capability note says why.

### Recipe 12 is a two-file recipe and says so

The session stand-in is one file in the distribution, what `auth-source` writes, and one plugin
that gives it commands and a rail item. The samples page already allows a recipe to live outside
`activate(ctx)` when the path says otherwise, and this is the first that does. The recipe shows the
generator's file by its generated name, unchanged, so that the reader who ran the generator has
nothing to edit; the plugin is the part that is theirs.

The plugin is the demo's `session.plugin.ts` and `session-actions.ts` reduced to their shape:
three commands gated by `access` so that sign-in shows only when signed out, and a rail item with
a menu that draws the display name or initials. The account switch between two roles stays, because
it is what makes gating visible on screen, which is the reason the stand-in exists.

*Alternative rejected: making recipe 12 a third shape in the auth guide only.* The guide gets a
section, because that is where a reader looks for "how does login work here". But the guide's code
is fragments inside a story, and a recipe is whole files with paths. Both, each in its form.

### The auth guide's pointer goes to the demo, not the testbed

The testbed weaver lives in `platform/libs/weavers`, is not published, and is not in `examples/`.
A reader from outside is sent to the platform's own test fixture. The pointer becomes
`demo/src/session`, which is a product built on the published packages and is what the section
describes. This is the one place this change points at the demo; the general question of how the
docs and the demo reference each other stays with `the-demo-points-at-the-docs`.

### The recipe table names what the generator writes, and what it does not yet

Recipe 12 joins the table with `auth-source --name dev` as the invocation that writes its first
file and the note that the plugin is yours. Recipe 11 joins the paragraph under the table that
names the recipes with no generator behind them, with one sentence that a generator is intended.
The table stays true on the day the follow-up lands by changing one row.

### The AI-readable files get exactly this change's additions

`llms.txt` gains the page in its weaver list with a one-line hook. `llms-full.txt` gains the
navigation family in the building-block bullet: the three tags, their attributes, the
`lw-nav-select` event with its `detail.path`, that the tree navigates nothing, `forgetLwNavFolds()`
for tests, and the two traps. Nothing else in those files is touched here, so that the audit in the
sibling change starts from a known state.

## Risks / Trade-offs

- **The page describes behaviour a future element change would contradict.** → Every statement
  on the page maps to a requirement in `ui-primitives` or `routing`, and the box at the top names
  them; a change to the element goes through those specs and finds the page from there.
- **Recipe 12 shows the generator's file, and the generator changes.** → The recipe names the
  generator invocation and shows its output as of this version; the follow-up change that extends
  `auth-source` updates the recipe in the same pull request, which the tasks there will say.
- **The stand-in reads like a login the platform ships.** → The auth guide's section and the
  recipe both open with the sentence that the platform owns no sign-in, and both say the stand-in
  is presentation for a product that has no backend yet.
- **The site build fails on a page missing from the sidebar.** → Adding the sidebar entry is its
  own task, before the build is run.

## Open Questions

None that change what gets built. Whether the follow-up generator is a new `navigation` generator
or an option on `weaver` is that change's question, and the recipe is the same either way.
